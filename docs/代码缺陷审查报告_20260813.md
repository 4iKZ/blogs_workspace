## 二、高严重程度缺陷

### B-H1. 文章搜索 `.or()` 未加括号，草稿/未发布文章通过公开接口泄露

- **文件**：`src/main/java/com/blog/service/impl/ArticleServiceImpl.java:546-549`
- **证据**：
```java
LambdaQueryWrapper<Article> queryWrapper = new LambdaQueryWrapper<>();
queryWrapper.like(Article::getTitle, keyword)
        .or()
        .like(Article::getContent, keyword);
queryWrapper.eq(Article::getStatus, 2); // 只搜索已发布的文章
```
- **问题**：MyBatis-Plus `.or()` 不加 `.and(w -> ...)` 分组，生成 SQL 为 `title LIKE ? OR (content LIKE ? AND status = 2)`。AND 优先级高于 OR，**标题命中但状态为草稿(1)/下线的文章也会被返回**。`/api/article/search` 为公开端点，等于公开泄露草稿内容。
- **同类问题**：`AdminServiceImpl.getUserList:97-107`、`getArticleList:191-199` 存在同样的 `.or()` 破坏 status 过滤问题。

### B-H2. 评论 AI 审核事件从未发布，违规评论直接公开

- **文件**：`src/main/java/com/blog/service/impl/CommentServiceImpl.java:142`；`event/CommentModerationEventListener.java`
- **证据**：全代码库 `new CommentModerationEvent(...)` **零匹配**——事件只被监听器 import，从未被 publish。`CommentServiceImpl.createComment()` 直接 `comment.setStatus(2)`（已通过/公开）。
- **问题**：异步 AI 评论审核（含把违规评论置为 status=3 下架的兜底逻辑）是永远不可达的死代码。评论提交即公开，只能依赖本地敏感词过滤，内容安全防线实际失效。

### B-H3. `@Transactional` 方法内 try-catch 吞异常，出错仍提交部分变更

- **文件**：`service/impl/ArticleServiceImpl.java:305-308, 366-369, 414-417`；`service/impl/UserFavoriteServiceImpl.java:120-127, 174-181`
- **证据**（publishArticle）：
```java
@Transactional
public Result<Long> publishArticle(...) {
    try {
        articleMapper.insert(article);          // 已执行
        String token = moderationSubmissionService.submitNew(article);
        ...
    } catch (RuntimeException e) {
        log.error("发布文章失败", e);
        return BusinessUtils.error(e.getMessage());   // 异常被吞，事务照常提交
    }
}
```
- **问题**：`@Transactional` 仅当异常传播出方法时才回滚。此处 catch 后返回 `Result.error`，事务照常提交。审核任务失败时草稿已被插入；`editArticle` 快照失败时更新已写入。`UserFavoriteServiceImpl` 更严重：连 `setRollbackOnly()` 都没调，收藏记录插入后计数更新失败 → 记录被提交、计数不一致（对比 `UserLikeServiceImpl:152` 有调用）。

### B-H4. 评论数扣减无下限保护，可被扣为负数

- **文件**：`service/impl/ArticleStatisticsServiceImpl.java:237`；`mapper/ArticleMapper.java:174-182`
- **证据**：
```java
// 实际使用的扣减（无 GREATEST 保护）：
int result = articleMapper.updateCommentCount(articleId, -count);
@Update("UPDATE articles SET comment_count = comment_count + #{increment}, ...")  // updateCommentCount

// Mapper 里存在但从未被使用的安全版本：
@Update("UPDATE articles SET comment_count = GREATEST(0, comment_count - 1) ... AND comment_count > 0")
int decrementCommentCountSafely(...);
```
- **问题**：删除评论时按 `commentsToDelete.size()` 批量扣减，一旦计数与真实记录不同步（如并发删除父/子评论、历史脏数据），`comment_count` 会被扣成负数并在前端展示。点赞/收藏都用了 `GREATEST` 安全版本，唯独评论数没有。

### F-H1. 分类文章页调用受保护接口，未登录用户被强制跳登录页

- **文件**：`frontend/src/views/CategoryView.vue:244-252`、`frontend/src/services/articleService.ts:73`；`config/SecurityConfig.java:71`
- **证据**：
```ts
axios.get<PageResult<Article>>("/article/category/" + categoryId.value, { params: { page, size } })
```
```java
.requestMatchers("/api/article/list", "/api/article/{id}", "/api/article/hot", "/api/article/recommended").permitAll()
... .anyRequest().authenticated()
```
- **问题**：`/category/:id` 路由本身是公开的，但请求 `/api/article/category/{id}` 是 4 段路径，不匹配 `{id}` 单段通配，落入 `anyRequest().authenticated()` → 未登录用户收到 401 → axios 拦截器刷新 token 失败 → 被踢到登录页。**未登录用户完全无法浏览分类文章列表**。

### F-H2. 敏感词管理列表永远为空（`res.records` 与后端 `items` 字段不匹配）

- **文件**：`frontend/src/views/admin/AdminSensitiveWordsView.vue:408`、`frontend/src/api/sensitiveWord.ts:3-9`；`common/PageResult.java:18`
- **证据**：
```ts
// 前端
wordList.value = res.records
// 后端 PageResult 序列化字段名
@JsonProperty("items")
private List<T> items;
```
- **问题**：后端分页列表字段是 `items`，前端读 `records`（本地声明的接口也是 `records`）。`res.records` 恒为 `undefined`，敏感词表格永远为空，管理员无法管理任何敏感词。

## 三、中严重程度缺陷（后端）

### B-M1. 评论列表 `status` 参数可被公开调用方任意指定 + 列表缓存 key 不含 status

- **文件**：`controller/CommentController.java:48`、`service/impl/CommentServiceImpl.java:186-218, 200`
- **问题**：`/api/comment/list` 是 permitAll 端点，`status` 直接透传，非管理员未强制为 2。传 `status=3` 可公开读取被 AI 拒绝下架的评论。且列表缓存 key 不含 status：先请求 status=3 会把被拒评论写入全局缓存，之后默认访客请求命中该缓存 → 缓存投毒。

### B-M2. GitHub OAuth 按邮箱静默绑定已有账号（账号接管风险）

- **文件**：`service/impl/UserServiceImpl.java:1383-1441`
- **问题**：GitHub 未公开邮箱时用 `githubUsername + "@github.placeholder"` 占位。攻击者可预注册 `victim@github.placeholder`，受害者走 OAuth 登录时 `github_id` 被绑定到该攻击者账号（`emailExistingUser.setGithubId(githubId)`），无需任何二次验证 → 账号接管。同处还以真实邮箱静默绑定已有账号。

### B-M3. `X-Forwarded-For` 直接信任，可绕过 IP 限流 / 伪造 lastLoginIp

- **文件**：`service/impl/UserServiceImpl.java:636-637, 1243-1265`
- **问题**：`getClientIp()` 直接读客户端可控的 `X-Forwarded-For` 头。密码重置验证码 IP 限流（20 次/小时）可被换头无限绕过；`lastLoginIp` 可被伪造。若部署在 Nginx 之后，nginx.conf 未统一覆盖该头（需确认）。

### B-M4. 全局异常处理回显内部异常消息

- **文件**：`exception/GlobalExceptionHandler.java:156-161`
- **问题**：`IllegalArgumentException` 的 `e.getMessage()` 原样返回；多个 Service catch 后 `BusinessUtils.error(e.getMessage())`。内部异常消息可能含文件路径、连接细节，泄露实现信息。

### B-M5. 附件上传无类型/大小校验，可在 public-read 的 TOS 上托管任意内容

- **文件**：`service/impl/FileUploadServiceImpl.java:84-148`；`application.yml:134`
- **问题**：`uploadFile` 仅校验 `file.isEmpty()`，无扩展名/MIME/大小限制，`Content-Type` 原样透传，TOS 为 `acl: public-read`。可上传 `.html`/`.svg` 作钓鱼/恶意托管。对比 `uploadImage` 有 `ValidatedImage` 校验。

### B-M6. “MD5 秒传”端点实际比对 SHA-256，功能失效

- **文件**：`controller/FileUploadController.java:69-73`；`service/impl/FileUploadServiceImpl.java:95, 243, 284`
- **问题**：`GET /file/check/md5/{md5}` 名称与参数是 md5，但入库用 `calculateSha256`，比对 `content_hash`（char(64)，SHA-256 长度）。前端按契约传 MD5 永远查不到 → 秒传/去重失效。

### B-M7. `deleteCategory` 查询 articles 表不存在的 `deleted` 列

- **文件**：`service/impl/CategoryServiceImpl.java:107-111`；`entity/Article.java:152-153`
- **证据**：`Article.deleted` 标注 `@TableField(exist = false)`，schema.sql 的 `articles` 表无 `deleted` 列（已核查），但 `deleteCategory` 用 `.eq(Article::getDeleted, 0)` 查询 → 该查询引用不存在列，含文章的分类删除会抛 SQL 异常（500），分类可能无法删除。

### B-M8. 点赞列表 total 与列表不一致（总数含已下线文章）

- **文件**：`mapper/UserLikeMapper.java:50-52` vs `87-95`
- **问题**：`countByUserId` 不过滤文章状态，`selectByUserId` 只返回 status=2 的文章。点过赞的文章下线/删除后，total > 实际列表数，末页为空。

### B-M9. 定时任务无分布式锁/Leader 选举，多实例重复执行

- **文件**：`schedule/*.java`、`event/PersistentCacheInvalidationScheduler.java:26`、`service/impl/ChunkedUploadServiceImpl.java:404`
- **问题**：`ArticleModerationSubmissionScheduler.recoverStaleProcessing` 跨实例会把他人进行中的 AI 审核判为 stale 重新调度 → 双审核；`PersistentCacheInvalidationScheduler` 两实例同时消费同一 ZSet 队列 → 重复失效。

### B-M10. 多级缓存实际只有 Caffeine L1 生效

- **文件**：`config/CacheConfig.java:67-77`
- **问题**：`CompositeCacheManager` 只返回第一个匹配的 Cache（Caffeine，30s TTL），Redis L2 永远不会被 `@Cacheable` 命中。多实例下热榜缓存无法跨实例失效，文档宣称的 L1→L2 架构未真正工作。

### B-M11. 文件上传配置接口回显 OSS SecretKey

- **文件**：`service/impl/SystemConfigServiceImpl.java:329-330`
- **问题**：SMTP 密码"只写不回显"，但 `ossAccessKey/ossSecretKey` 明文回显给前端，XSS/越权时云存储密钥泄露。

### B-M12. 点赞后评论列表/热门评论缓存中的 likeCount 陈旧

- **文件**：`service/impl/CommentServiceImpl.java:569-583`
- **问题**：`likeComment/unlikeComment` 的 afterCommit 只清点赞状态和评论详情 key，**不清列表/热门缓存**。匿名用户看到的点赞数陈旧最多 1 小时（列表 TTL 1h、热门 30min）。

### B-M13. 缓存清理在事务提交前执行（cache-aside 竞态）

- **文件**：`service/impl/CommentServiceImpl.java:171, 408`
- **问题**：`createComment`/`deleteComment` 在事务内清缓存后提交，窗口期内并发读 miss 后查库（读不到新数据）并回填旧缓存（1h TTL）→ 新评论最多缺席 1 小时 / 已删评论残留 1 小时。应在 `afterCommit` 清缓存。

### B-M14. 并发删除父评论与子评论，comment_count 双重扣减

- **文件**：`service/impl/CommentServiceImpl.java:357-411`
- **问题**：删除父评论（锁 key `comment:delete:<父id>`，级联扣减含子数量）与直接删除子评论（锁 key 不同）可并发 → 子评论扣两次，叠加 B-H4 可为负数。

## 四、中严重程度缺陷（前端）

### F-M1. 文件管理页分页失效（后端返回纯数组，前端按 PageResult 处理）

- **文件**：`frontend/src/services/fileService.ts:19-41`；`views/admin/AdminFilesView.vue:216-228`；`service/impl/FileUploadServiceImpl.java:190`
- **问题**：后端 `/file/list` 返回 `Result<List<FileInfoDTO>>`（纯数组），前端 `total = data.length`（当前页长度）→ `el-pagination` 显示 total=10，第 2 页起永远无法访问。

### F-M2. 搜索页快速连续搜索响应乱序 + 改每页条数不重置页码

- **文件**：`frontend/src/views/SearchView.vue:74-78, 109-112`
- **问题**：`watch(keyword)` 直接触发请求，无防抖/无请求序号/AbortController → 旧请求后返回会覆盖新关键词结果。`handleSizeChange` 未把 `currentPage` 重置为 1 → 停在超范围页码返回空列表。

### F-M3. 用户主页标签切换三重触发重复请求

- **文件**：`frontend/src/views/UserProfileView.vue:26-30, 380-452`
- **问题**：`el-tabs` 同时绑 `@tab-change` + `@tab-click`，另有 `watch(activeMainTab)` → 一次切换最多触发 3 次请求，且异步返回顺序竞争。

### F-M4. 评论分页控件永不显示（total 从未赋值）

- **文件**：`frontend/src/components/comment/CommentSection.vue:85-98, 200-238`
- **问题**：`const total = ref(0)`，`loadComments` 中从未给 `total` 赋值（只赋了展示用的 `totalComments`），`v-if="total > pageSize"` 恒不成立 → 超过 10 条的评论永远无法翻页查看。

### F-M5. 页面刷新时一次瞬时网络错误即强制登出

- **文件**：`frontend/src/store/user.ts:78-94`
- **问题**：`performSessionInitialization` 任何失败（包括断网/后端抖动的瞬时错误）都 `clearUserInfo()` 清空登录态，且 `sessionInitialized=true` 使本会话不再重试。访问 token 仍有效却被无差别清除，用户被迫重新登录。

## 六、建议修复优先级

**P0（安全/数据泄露，尽快修复）**
1. B-H1 搜索 `.or()` 分组（`title OR content` 用 `and(w -> like(title).or().like(content))`）—— 草稿泄露
2. B-H3 事务吞异常 —— catch 中调 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`
3. B-M1 评论列表 status 参数强制为 2 + 缓存 key 加 status
4. F-H1 分类接口加入 permitAll（或改为 `/api/category` 聚合）
5. B-M2 / B-M3 GitHub 绑定与 XFF 信任

**P1（功能/一致性）**
6. F-H2 敏感词列表字段改 `items`
7. B-H4 评论数扣减改用 `GREATEST` 安全版本
8. F-M1 / F-M4 分页契约对齐
9. B-M6 MD5/SHA-256 契约统一
10. B-M12 点赞后清列表/热门缓存

**P2（架构/性能）**：B-M9 定时任务加锁、B-M10 二级缓存架构、B-M13 afterCommit 清缓存、M2 搜索防抖、M3 标签页去重。
