# 数据库停机恢复操作手册

## 安全边界

生产应用不提供在线数据库恢复能力。`POST /api/system/backup/restore/{backupId}` 已移除，调用会返回 404。后台只保留备份创建、列表、下载和删除功能；恢复必须由具有主机和数据库运维权限的人员在维护窗口内执行。

恢复脚本不会保存、拼接或传递数据库密码。请通过受控的 MySQL 客户端登录方式（例如受限的 `~/.my.cnf`、Windows 用户配置或短生命周期的运维环境变量）提供认证信息，切勿把密码写入命令历史或脚本。

## 恢复前检查

1. 宣布维护窗口，停止应用实例、异步任务和写流量，并确认网关已进入维护模式。
2. 下载并校验待恢复 SQL 文件，确保它来自受信任的备份来源。
3. 在目标主机确认 `mysql` 与 `mysqldump` 可用，并确认该账号具有目标库的备份、恢复和查询权限。
4. 准备受控目录和足够磁盘空间：脚本默认在自身同级的 `.restore-safety` 创建当前数据库的安全备份及 SHA-256 校验文件。可用 `BLOG_RESTORE_SAFETY_DIR` 指定已存在或可创建的私有目录；该目录不得是符号链接/重解析点，也不能是根目录。脚本会打印实际安全备份与校验文件路径。

脚本会要求两次输入完全一致的数据库名，以及输入 `MAINTENANCE`。数据库名仅接受字母、数字和下划线，以避免把交互输入作为 SQL 或 shell 代码执行。

## 执行恢复

Linux/macOS（Bash）：

```bash
chmod 700 scripts/restore-backup.sh
scripts/restore-backup.sh /srv/backups/blog-20260727.sql
```

Windows（PowerShell）：

```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\scripts\restore-backup.ps1 -BackupPath 'D:\backups\blog-20260727.sql'
```

两份脚本按以下顺序工作：检查客户端、验证文件和双重确认、在私有目录中原子创建安全备份、写入 SHA-256、在同一个恢复会话尾部执行 `SET FOREIGN_KEY_CHECKS=1`、验证 `users`、`articles`、`comments` 三张核心表，以及查询文章和评论的实际孤儿引用。任一步骤失败都会停止，且会打印安全备份位置；脚本不会删除安全备份。

## 恢复后的验证和回滚

1. 使用只读账号抽查核心表行数和最近文章。
2. 查看应用迁移版本与预期一致；脚本已在恢复会话中重新启用外键检查并验证核心关联不存在孤儿数据。
3. 仅在验证完成后解除维护模式并逐步启动应用实例，观察健康检查、错误日志和关键读写请求。
4. 若恢复或验证失败，保持维护模式，使用脚本生成的 `safety-<database>-<random>.sql` 作为输入再次执行同一脚本进行回滚；不要尝试在线 HTTP 恢复。

建议在预发布环境先针对脱敏备份演练一次完整的成功、错误凭据、损坏 SQL 和恢复失败流程。
