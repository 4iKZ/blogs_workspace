## 1. 执行摘要

项目采用标准的前后端分离结构：

```text
Vue Router -> Pinia -> Axios 拦截器 -> /api
                                      |
Spring Security JWT Filter -> Controller -> Service -> Mapper
                                              |          |
                                              |          +-> MySQL
                                              +-> Redis / TOS / 邮件 / 异步事件
```

当前最主要的风险不是单个页面错误，而是后端授权边界不完整：

- 部分高权限接口未位于 `/api/admin/**` 下，因而只要求“已登录”，普通用户可以执行用户管理、系统配置、备份恢复和数据导出。
- `permitAll()` 使用过宽的路径通配符，将分类写操作、统计计数修改和统计清理一并公开。
- 存在无需验证码即可重置任意账号密码的兼容接口。
- 仓库包含多组疑似真实生产凭据，必须按“已经泄露”处理。

### 2.2 测试结果解释

后端测试失败不能简单归因于业务代码：

- 多个 Spring 测试上下文共享 `jdbc:h2:mem:testdb;DB_CLOSE_DELAY=-1`，重复执行 `schema-h2.sql` 后出现 `Table "USERS" already exists`。
- `system_config` 测试表缺少 Mapper SQL 使用的 `deleted` 字段。
- 测试默认尝试连接真实 Redis、远程 MySQL 和 TOS。
- `HardcodedTOSUploadTest` 在本次运行中通过，源码显示其确实执行了 TOS `putObject` 和 `deleteObject`。

因此，当前测试结果既包含真实回归，也包含测试基础设施造成的大量级联错误。详见 P1-09。

## 3. P0 / 严重问题

## P0-01 仓库提交了生产数据库、Redis、AI、JWT、TOS 和 GitHub OAuth 凭据

**证据**

- `src/main/resources/application.yml:9-11`：远程数据库地址和默认密码。
- `src/main/resources/application.yml:25-41`：Redis 主机和明文密码。
- `src/main/resources/application.yml:67-69`：AI API Key。
- `src/main/resources/application.yml:113-114`：JWT 与刷新令牌默认密钥。
- `src/main/resources/application.yml:127-128`：TOS Access Key 与 Secret Key。
- `src/main/resources/application.yml:172-174`：GitHub OAuth Client Secret。
- `src/test/java/com/blog/HardcodedTOSUploadTest.java:29-34`、`TOSConnectionTest.java:22-27`：测试代码也带有 TOS 凭据回退值和真实桶信息。

**触发与影响**

- 任何能读取仓库或 Git 历史的人都可能访问数据库、缓存、对象存储、OAuth 应用或第三方 AI 账户。
- 泄露的 JWT 密钥可能允许伪造登录身份。
- 删除当前文件中的值并不能消除 Git 历史里的泄露。

**根因**

- 生产配置直接提交到版本库，并为环境变量提供了真实敏感值作为默认值。
- 测试使用真实凭据作为环境变量缺失时的 fallback。

**修复建议**

1. 立即轮换全部相关凭据；在轮换完成前按已泄露处理。
2. 配置文件只保留 `${ENV_NAME}`，敏感项不得提供真实默认值。
3. 使用 Git 历史清理工具移除旧值，并评估所有 fork、CI 日志和构建产物。
4. 在 CI 加入 secret scanning 和提交前扫描。

**验收**

- 历史扫描不再检测到旧凭据。
- 旧凭据全部失效。
- 缺少必需环境变量时应用明确拒绝启动，而不是回退到生产密钥。

## P0-02 未认证用户可以绕过验证码重置任意账号密码

**证据**

- `src/main/java/com/blog/config/SecurityConfig.java:48` 将 `/api/user/reset-password` 设为公开。
- `src/main/java/com/blog/controller/UserController.java:139-145` 只接收 `email` 和 `newPassword`。
- `src/main/java/com/blog/service/impl/UserServiceImpl.java:512-534` 根据邮箱查用户后直接更新密码，没有校验验证码、旧密码、一次性 token 或登录身份。
- 同一项目已经存在正确的验证码流程：`/api/user/password/reset/send` 与 `/api/user/password/reset`。

**复现**

```http
POST /api/user/reset-password?email=victim@example.com&newPassword=<符合策略的新密码>
```

请求不需要 Authorization，也不需要邮箱验证码。

**影响**

- 知道用户邮箱即可接管账号。
- 管理员邮箱一旦暴露，可进一步接管管理后台。

**根因**

- 旧兼容接口未删除，且安全配置继续公开该路径。

**修复建议**

- 立即删除或永久禁用该接口，只保留带验证码的一次性重置流程。
- 密码重置成功后撤销该用户全部 access token 和 refresh token。
- 增加未认证攻击回归测试，确保无验证码请求始终失败。

## P0-03 普通登录用户可以调用 `/api/user/admin/**` 管理其他用户

**证据**

- `src/main/java/com/blog/controller/UserController.java:167-189` 暴露：
  - `GET /api/user/admin/list`
  - `PUT /api/user/admin/status/{userId}`
  - `DELETE /api/user/admin/{userId}`
- `src/main/java/com/blog/config/SecurityConfig.java:83-86` 只对 `/api/admin/**` 要求管理员角色，随后 `.anyRequest().authenticated()`。
- 上述 `/api/user/admin/**` 不匹配 `/api/admin/**`，因此普通用户只要登录即可调用。
- Controller 与 `UserServiceImpl.java:636-672` 没有二次角色校验。

**影响**

- 普通用户可枚举用户资料、禁用账号和删除任意用户。
- 可用于删除管理员或批量破坏账号数据。

**修复建议**

- 删除重复的 `/api/user/admin/**` 管理接口，统一使用已经受保护的 `/api/admin/users/**`。
- 若必须保留兼容路径，显式配置 `.hasRole("admin")`，并在方法层增加 `@PreAuthorize` 作为纵深防御。
- 增加“普通用户返回 403、管理员成功”的端到端测试。

## P0-04 普通登录用户可读取 SMTP 密码并修改全部系统配置

**证据**

- `src/main/java/com/blog/config/SecurityConfig.java:57-58` 只公开网站配置读取，没有为其余 `/api/system/config/**` 设置管理员约束。
- `src/main/java/com/blog/controller/SystemConfigController.java:26-97` 的读取、单项更新、批量更新、网站/邮件/上传配置更新均无角色校验。
- `src/main/java/com/blog/service/impl/SystemConfigServiceImpl.java:275-289` 将真实 `smtpPassword` 放入响应 DTO。
- `SystemConfigServiceImpl.java:292-308` 允许调用者更新 SMTP 账号、密码和发件人。
- `SystemConfigServiceImpl.java:295` 还会把含 SMTP 密码的 DTO 写入日志。

**影响**

- 任意普通用户可窃取 SMTP 凭据。
- 可篡改站点开关、注册/评论策略、邮件服务器和上传策略。
- 明文日志进一步扩大密码暴露面。

**修复建议**

- 仅允许管理员访问所有非公开系统配置端点。
- 读取邮件配置时永不返回已保存密码，只返回 `passwordConfigured: true/false`。
- 更新时使用“空值表示保留原密码”的语义。
- 删除包含完整 DTO 的日志，轮换可能已经暴露的 SMTP 密码。

## P0-05 普通登录用户可导出、下载、删除备份并触发数据库恢复

**证据**

- `src/main/java/com/blog/controller/DataBackupController.java:27-118` 位于 `/api/system/backup/**`，包含备份、恢复、全量用户/文章/评论导出、下载和删除。
- `SecurityConfig.java:83-86` 仅保护 `/api/admin/**`；这些接口最终只要求登录。
- `DataBackupController.java:62-80` 参数可为空，意味着可导出全部用户、文章或评论。
- `DataBackupController.java:96-117` 直接把备份/导出文件作为文件响应下载。

**影响**

- 普通用户可以导出并下载全量业务数据。
- 可以删除备份或触发数据库恢复，造成服务中断和数据回滚。

**修复建议**

- 将全部备份接口迁移到 `/api/admin/backup/**` 或显式要求管理员角色。
- 恢复数据库应增加二次确认、审计记录和并发互斥。
- 下载使用不可猜测的一次性 token 或经授权的资源 ID。
- 为普通用户访问所有备份端点补充 403 回归测试。

## 4. P1 / 高优先级问题

## P1-01 `/api/category/**` 的公开通配符同时公开了增删改操作

**证据**

- `SecurityConfig.java:61-62` 对 `/api/category/**` 使用 `permitAll()`，没有限定 HTTP 方法。
- `CategoryController.java:41-57` 在同一路径下提供 POST、PUT 和 DELETE。
- `CategoryControllerTest` 甚至以 `addCategory_shouldBePublic`、`updateCategory_shouldBePublic`、`deleteCategory_shouldBePublic` 命名测试，错误地固化了当前授权行为。

**影响**

- 未登录攻击者可创建、修改或删除文章分类。

**修复建议**

- 只对分类 GET 请求公开；POST/PUT/DELETE 要求管理员。
- 安全测试应验证未登录返回 401、普通用户返回 403、管理员成功。

## P1-02 `/api/statistics/**` 公开了计数篡改和统计数据清理

**证据**

- `SecurityConfig.java:71-72` 公开整个 `/api/statistics/**`。
- `ArticleStatisticsController.java:53-95` 提供浏览、点赞、评论、收藏计数增减接口。
- `WebsiteStatisticsController.java:87` 提供 `DELETE /api/statistics/website/clean`。

**影响**

- 未登录攻击者可批量操纵热度与互动计数。
- 可触发统计清理，破坏访问分析数据。

**修复建议**

- 仅公开必要的只读统计与受控的浏览记录接口。
- 点赞、评论、收藏计数只能由对应业务事务内部更新，不应作为公共 API。
- 清理接口只允许管理员，并增加审计与参数上限。

## P1-03 任意登录用户可删除任意评论，且异常可能造成部分删除提交

**证据**

- 实际删除路由是 `DELETE /api/comment/{commentId}`（`CommentController.java:117-120`）。
- `SecurityConfig.java:74` 配置的是不存在的 `/api/comment/*/delete`，实际路由最终仅受 `.anyRequest().authenticated()` 保护。
- `CommentController` 未传当前用户 ID。
- `CommentServiceImpl.java:327-404` 删除评论及全部子评论，没有校验评论作者、文章作者或管理员身份。
- `CommentServiceImpl.java:405-407` 在 `@Transactional` 方法内部吞掉异常并返回错误，可能让已经执行的部分删除被提交。

**影响**

- 任意普通用户可删除他人评论及其整棵回复树。
- 中途失败时可能出现评论、点赞记录、统计计数不一致。

**修复建议**

- 删除权限限定为评论作者、文章作者或管理员。

## P1-05 公开文章列表允许调用者指定状态并读取草稿/下线文章

## P1-06 用户状态语义不一致，禁用账号的现有 token 仍可能有效

**证据**

- `database/schema.sql:45` 定义 `1=正常、2=禁用、3=删除`。
- `UserServiceImpl.java:235-241` 登录时拒绝所有非 1 状态。
- `UserServiceImpl.java:330-332` 刷新 token 时却只拒绝状态 0，状态 2/3 可继续刷新。
- `UserServiceImpl.java:652-654` 更新状态时只在状态 0 删除 refresh token。
- `CustomUserDetailsServiceImpl.java:40-44` 构造的 `UserDetails` 默认始终 enabled，没有映射数据库 status。
- `JwtAuthenticationFilter.java:41-62` 只检查 JWT、黑名单和 `userDetails.isEnabled()`。

**影响**

- 按数据库约定设置为状态 2 的禁用用户，可能继续刷新和使用 token。
- 即使使用状态 0，已签发 access token 也未被整体撤销。

**修复建议**

- 统一状态枚举，禁止在 Controller、SQL 和 Service 中使用互相冲突的裸整数。
- `UserDetails.isEnabled()` 必须映射 `status == ACTIVE`。
- 增加按用户维度的 token version/revoked-at 校验，禁用、删除、改密时使全部 token 失效。

## P1-07 登录验证码校验失败后仍继续认证

**证据**

- `UserServiceImpl.java:212-217` 调用验证码校验，但失败后只记录日志。

- 前端 `authService.ts:3-8` 和登录页将验证码作为必填登录参数，表明产品预期验证码生效。

**影响**

- 登录验证码没有实际防护作用。
- 在没有其他登录限流/失败锁定证据的情况下，可被用于自动化密码喷洒和暴力破解。

**修复建议**

- 验证码失败立即拒绝登录，并一次性消费验证码。
- 同时增加按账号和 IP 的失败计数、渐进延迟和限流。

## P1-08 公开头像上传可被匿名滥用并只信任客户端 MIME

**证据**

- `SecurityConfig.java:53` 将 `/api/user/avatar/upload` 设为公开。

**影响**

**修复建议**

- 上传必须认证并按用户/IP 限流。
- 服务端实际解码图片、限制像素和格式，重新编码后再上传。
- 记录并清理未被用户资料引用的临时对象。

## 5. P2 / 中优先级问题

## P2-01 token 刷新失败时，并发等待请求永久 pending（✅ 已完成）

**证据**

- `frontend/src/utils/axios.ts:51-72` 只保存成功回调，没有 reject 回调。
- 并发 401 在 `axios.ts:124-131` 订阅刷新结果。
- 只有刷新成功时 `axios.ts:138` 调用 `notifyTokenRefreshed`。
- 刷新失败的 `catch`（`axios.ts:143-146`）只清理登录态，没有 reject/清空订阅者。

**影响**

- refresh token 过期时，同时发出的部分 API Promise 永远不结束。
- 页面 loading、按钮禁用或路由等待状态可能永久卡住。

**修复建议**

- 队列保存 `{resolve, reject}`，成功全部 resolve，失败全部 reject 并清空。
- 为“多个并发 401 + refresh 失败”增加前端单元测试。

## P2-02 公开用户主页与后端授权规则冲突（✅ 已完成）

**证据**

**影响**

**修复建议**

- 若用户主页本应公开，只开放明确的公开信息与已发布文章 GET 路径。

## P2-03 备份与导出下载的前端实现无法处理后端二进制响应（✅ 已完成）

**证据**

**影响**

**修复建议**

- 下载使用独立原始 Axios 实例或允许 blob 的响应分支。
- 设置 `responseType: "blob"`，解析 `Content-Disposition`，创建临时 URL 并触发下载。

## P2-04 管理员刷新后台页面会因角色尚未恢复而被重定向（✅ 已完成）

**影响**

**修复建议**
